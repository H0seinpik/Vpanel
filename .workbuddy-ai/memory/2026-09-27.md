# 2026-09-27 — VPanel

## Session goal

Fix the user's three reported symptoms, which all traced back to the panel↔node
link:

1. configurations created in the panel did not connect
2. the configuration traffic ceiling never fired
3. traffic was not counted in the Configs tab

## Root causes found (all three were real, independent bugs)

### 1. Duplicate inbound tag → Xray refused to start entirely

`renderXrayConfig()` assigned the per-config tag with `inbound.tag = inbound.tag ?? ...`.
The generator already emits a protocol-based tag (`vless-in`), so the fallback
never fired. Two VLESS configurations therefore produced two inbounds both
tagged `vless-in`, and Xray aborted with:

```
Failed to start: main: failed to create server > app/proxyman/inbound: existing tag found: vless-in
```

Xray failing to start takes down **every** inbound, not just the colliding one —
which is why nothing connected at all. Fixed by assigning the tag
unconditionally (`vpanel-<id suffix>`) with a `usedTags` set for disambiguation.

### 2. A stale worker process was overwriting the node config

An old `workers/index.ts daemon` process (started before the
`pinnedPeerCertSha256` change) was still alive and re-rendered `config.json`
from its in-memory old code every 15s, reverting the correct config back to
`allowInsecure: true`. Verified by watching the file mtime freeze once the
process was killed. Lesson: after editing worker code, always confirm no old
worker process is still running.

### 3. The collector emitted deltas, the ledger expects per-window totals

`windowKeyFor()` rounds to the minute, and `recordTrafficSamples()` treats
`uploadBytes` as the **cumulative total for that window**, applying only the
difference against the existing ledger row (that is what makes collection
idempotent). But `collectXrayTraffic()` emitted **deltas since the last
snapshot**.

Since the reconcile worker runs every 15s, four collections land in one
one-minute window and three of them were silently netted away.

Two further flaws in the same function:

- **First sighting used the current counter as the baseline**, so a client that
  only appears in the stats after its first connection had all of that traffic
  discarded. (The function also returned early without writing a baseline when
  the node had no user stats at all, which made this the normal path, not an
  edge case.)
- **Window rollover reset the baseline to the current value**, dropping
  whatever arrived between the last collection and the rollover.

Rewritten as `computeWindowTotals()` — pure, exported, unit-tested:

| transition | baseline |
| --- | --- |
| first sighting | `0` (the node counter is cumulative from process start) |
| window rollover | previous raw value (carries the boundary traffic) |
| node restart (counter went backwards) | `-(recorded so far)` so `raw - base` preserves the window total |

## Robustness changes

- `queryUserStats()` used `spawnSync`, which **blocks the whole worker** and
  fails outright with `EBUSY` on Windows in some environments (another instance
  of the image running, or a security product holding the file). Replaced with
  an async `execCapture()`; `isXrayRunning()` and `stopXray()` followed.
- A failed stats query used to return an empty map — indistinguishable from
  "no traffic", which is how accounting can stop for days unnoticed. It now
  records `lastStatsError`, logs a warning from the worker, and is exposed on
  `getXrayStatus()`.

# 2026-09-27 (later) — configuration ceilings overshot their limit

## Reported

> "when i create config and at the limit there is only gb and if i set it to
> 0.006 its turn to mb thats fine but when actually hit the limit it not stop
> the config and it will go far than the limit"

A limit applied **after** creation (from the config detail page) appeared to
work; a limit supplied **at creation** did not.

## What was actually wrong

Storage was fine — verified directly: `trafficLimitGb: 0.006` stores
`6442451` bytes on the `Configuration` row, identical to the update path.

The real cause was **scheduling**. Configuration ceilings were only evaluated by
`enforceConfigStatuses()` inside the enforcement worker, which runs every
`max(TRAFFIC_INTERVAL_SECONDS * 5, 300s)` = **600 s (10 minutes)**, while the node
is reconciled every **15 s**. A configuration on a small allowance therefore
served for up to ten minutes past its ceiling.

Confirmed against the live database: the operator's VMESS configuration had
`limit = 6442451` (0.006 GB) and `trafficUsedBytes = 19575322` — **3× over its
limit** before anything stopped it. The perceived difference between the two
cases was just where in the 10-minute window the change happened to land.

## Fix

`workers/xray-worker.ts` now runs the ceiling pass on every reconcile tick, and
the order inside the tick was chosen deliberately:

1. **collect** — record the node's counters first, so the final bytes of a
   configuration that is about to be removed are still captured;
2. **enforce** — apply each configuration's ceiling against the figures just
   recorded, so the same tick that notices an overshoot stops serving it.
   Enforcing before collecting would delay the drop by a whole extra interval;
3. **reconcile** — render the node config with the resulting statuses.

Measured after the fix: **stopped 10 s after the ceiling was crossed** (was up
to 600 s).

## Port sharing — many configurations on one port 443 (fallbacks)

Requested: *"how can i make unlimited config on port 443"* → chose **Build 443
fallback sharing** + **Must be on 443**.

A TCP port belongs to one process at a time, so "many listeners on 443" is
impossible at the OS level. Xray's answer is **fallbacks**: one listener holds
443 and routes each connection to a per-configuration loopback inbound by
request path.

### Built

- `src/services/port-sharing.ts` (pure, unit-tested) — the whole routing policy:
  `shareIneligible()` (only VLESS/Trojan, must be TLS, transport must expose a
  path), `sharePathFor()`, `internalPortFor()` (deterministic, so a no-op
  reconcile does not reshuffle ports), `planPortSharing()` (unique paths and
  ports, duplicate paths disambiguated), `resolvePortLayout()` (one config →
  direct inbound; two or more → shared).
- `renderXrayConfig()` rewritten to group configurations by port and emit either
  a direct inbound or the fallback structure: **one tagless VLESS+TLS listener**
  on the public port + one loopback inbound per configuration + a blackhole
  fallback for unmatched traffic.
- `assertConfigIsServable()` now ALLOWS several configurations on one port when
  every one of them is eligible, and explains precisely which one blocks sharing
  when it is not.
- Wizard: detects that the chosen port is shared, auto-seeds a unique path, and
  explains the routing. A port that is taken is only an error when the
  configurations genuinely cannot share.

### Constraints (cannot be engineered away)

1. **The public inbound must carry NO tag.** Xray requires a fallback parent to
   be tagless; its `fallback can only be used in tagless inbound` error is
   otherwise fatal to the whole process.
2. **Only VLESS and Trojan support fallbacks.** A VMess configuration on a
   shared port binds it and then carries nothing — a silent failure, so it is
   refused up front.
3. **TLS is required**; the transport must expose a path (ws / httpupgrade /
   xhttp / grpc). Sharing routes on the request path.
4. Each member binds `127.0.0.1` on a loopback port derived from its id; the
   public listener is the only entry point.

### Verified on the live node

- `xray run -test` on the rendered shared config → **`Configuration OK.`**
- Three VLESS+TLS+ws configs on 443 with **no path supplied** → renderer
  generated unique paths → **3/3 connected through the single port 443**.
- Rendered shape confirmed: one tagless 443 listener, 3 `path→port` routes, plus
  a blackhole; 3 loopback member inbounds each with its own client.
- 208/208 tests pass (was 187; +21 in `tests/port-sharing.test.ts`), tsc clean.

### Supervisor race fixed (found while testing)

`stopXray()` fired `taskkill` but did not wait, so starting a replacement in the
window before the old process released the port failed with a bind error and was
reported as "Xray FAILED to start" while the old instance was still serving.
Now: `stopXray()` waits (bounded) until no Xray remains; a bind-race failure is
retried once; and if a start fails while something is still serving, the message
says `the previous Xray instance is still serving (restart pending)` instead of
claiming the node is down.

**Reminder (rule 4):** a running worker races any manual reconcile. Two writers
to `config.json` every 15 s produced a misleading single-inbound render during
testing. Stop the worker before diagnosing by hand.

## The TLS certificate had no generator — found while writing the 443 guide

Writing the "recreate them as VLESS + tls + ws" guide surfaced a real gap: **the
certificate pair at `C:\xray\cert.pem` / `key.pem` was created by hand, and
nothing in the repo could recreate it.** `install-xray.ps1` does not generate one
and no `.bat`/`.ps1` mentions `cert.pem`. Yet every TLS configuration (Trojan,
VLESS+TLS, anything sharing a port) is **skipped** without it, and the pin baked
into every issued client link depends on it. Lose that file and every TLS config
dies silently with no recovery path.

### Added `xray-gencert.bat` + a `gencert` action in `windows/xray.ps1`

- **Refuses to overwrite an existing pair** unless `-Force` is given, and says
  why: replacing it changes the pin, so every client link already handed out
  stops working. This is the whole point — silent cert rotation is a footgun.
- Defaults the certificate name to the machine's non-private A record, falling
  back to `vpanel`. Names the cert after what the client actually connects to.
- **Writes the PEM as ASCII with LF endings, no BOM.** PowerShell 5.1 would emit
  a UTF-8 BOM and CRLF, and OpenSSL refuses a BOM — the certificate would be
  unreadable by Xray. Uses `[System.IO.File]::WriteAllText` with
  `ASCIIEncoding`, not `Set-Content`.
- Prints the resulting `Leaf SHA256` so it can be eyeballed against the panel.
- Uses `xray tls cert -json` and splits stdout. **Do not use `-file`** — that
  writes a combined PEM, not the separate cert/key the panel expects.

### Two things learned about the Xray CLI (easy to get wrong)

- `xray tls cert` **generates** a certificate. It has a `-file` flag that looks
  like it reads one. Calling it to "inspect" a cert silently produces a brand new
  one and had me briefly convinced the panel's pin was wrong — the three
  "different" certs I saw were three freshly generated ones. The command that
  reads a cert is `xray tls hash --cert <path>` (note: `--cert`, not `-file`).
- `xray help tls` is the reliable way to discover this; the subcommands are
  `cert` (generate), `hash` (read), `ping`, `ech`.

**Confirmed the panel's pin is correct:** `certificatePin()` returns
`24098dd21a1a8f23f9d8ed96fb5f943479f718c8fd18ce418e1bad5b7502fd72`, and `xray tls
hash --cert C:/xray/cert.pem` reports exactly the same. The pinning path was
never broken.

## The certificate panel crashed the wizard — my own bug

Reported: *"Application error: a client-side exception has occurred"*.

### Cause

`useApi` returned the payload **unwrapped**, but I typed the call as
`useApi<{ data: CertificateStatus }>` and read `certificate.data.data.tlsConfigsWillServe`.
The second `.data` was `undefined`, so the wizard threw the moment the operator
picked `security = tls` on step 5.

The contract, from `apiFetch` in `src/lib/api-client.ts`:

| response has sibling keys? | what `api.get()` returns |
| --- | --- |
| yes (`pagination`, counters) | the **whole** envelope — keep `.data` |
| no (a bare `{ data }`) | `payload.data` — **already unwrapped** |

My endpoint returned a bare `{ data }`, so it was unwrapped. All eight existing
`useApi<{ data: … }>` calls are list endpoints that return `pagination`, which is
why the pattern looked correct and was not.

**TypeScript could not catch this.** The annotation was a *lie*, not a mismatch —
`{ data: CertificateStatus }` type-checked fine, and `tsc --noEmit` was clean on
both sides of the bug. Only a runtime shape assertion finds it.

### Fix

- Read the status directly: `certificate.data.tlsConfigsWillServe` (flat).
- Moved the payload builder into `src/server/services/certificate-status.ts`.
  It **cannot live in the route file** — a Next.js route module may only export
  handlers, and exporting it produced
  `error TS2344: … does not satisfy the constraint '{ [x: string]: never; }'`.
- The wizard now imports `CertificateStatus` from that shared module instead of
  keeping its own copy, so client and server cannot drift again. The module has
  zero imports, so nothing server-only can leak into the browser bundle.
- `grep -rn '\.data\.data\.' src` returns nothing; keep it that way.

### Tests

`tests/certificate.test.ts` grew from 4 to **9 tests**, five of them on the real
payload shape: healthy pair serves with `fix: null`; a cert without its key counts
as absent (`present: false`); a missing pair names `xray-gencert.bat`; no field
can contain `BEGIN` or `PRIVATE KEY`; and the object is **flat** — it must expose
`tlsConfigsWillServe`/`pinShort` at the top level and must **not** have a nested
`data` property, which is precisely the regression.

### Verified

- 217/217 tests (13 files), tsc clean, `next build` succeeds.
- Rebuilt and restarted the web server; the built bundle contains **zero**
  `certificate.data.data` references and does contain `tlsConfigsWillServe`.
- `/` → 307, `/login` → 200, `/api/xray/certificate` → 401 unauthenticated.
- The worker (PID 332) was left running untouched; `.vpanel/runtime.json` updated

### The important finding: fix it IN PLACE

`updateConfig()` accepts a `params` change including `network`, and the
`ConfigAssignment.credential` row is **untouched**. So the operator never needs to
delete and recreate — which would lose the credential and the traffic history.
