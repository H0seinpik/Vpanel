# 2026-10-24

## Phase 1 of the 3x-ui routing port — Prisma schema (DONE)

- Added 4 additive models + 1 enum to `prisma/schema.prisma`:
  - `Inbound` — raw Xray inbound: `tag` (unique per server), `protocol`, `listen`,
    `port`, plus `settings` / `streamSettings` / `sniffing` as JSON, `sortOrder`,
    `enabled`.
  - `Outbound` — `tag`, `protocol`, `settings`, `streamSettings`, `sendThrough`.
  - `RoutingRule` — `sortOrder`, `outboundTag`, `balancerTag`, `inboundTags[]`,
    `domain[]`, `ip[]`, `port`, `sourceIp[]`, `sourcePort`, `protocol[]`, `network`.
  - `ReverseProxy` — `role` (BRIDGE | PORTAL), `tag`, `domain`; enum
    `ReverseProxyRole`.
- All four belong to `Server` (`onDelete: Cascade`). `createdById` is a plain nullable
  string — the same convention `Configuration` already uses — so **`User` is untouched**.
  `Server` gained 4 back-relation arrays (additive only). No existing column changed.
- Migration: `prisma/migrations/20261024170000_add_advanced_routing/migration.sql` —
  purely additive (`CREATE TYPE` + 4 × `CREATE TABLE` + indexes/FKs, **no `ALTER` on any
  existing table**). Applied with `migrate deploy`.
- `migrate dev` FAILED with **P3014**: the DB user cannot create a shadow database.
  Workaround used: `migrate diff --from-schema-datasource prisma/schema.prisma
  --to-schema-datamodel prisma/schema.prisma --script` → then `migrate deploy`.
- Verified via `.vpanel/verify-phase1.ts`: all 4 tables + `ReverseProxyRole` exist, the
  migration is recorded, and existing data is intact (16 configurations, 1 server,
  3 users).
- `prisma generate` is BLOCKED by `EPERM` on `query_engine-windows.dll.node` — the
  running panel + worker hold it. The client must be regenerated after stopping them
  (`stop.bat` → `prisma generate` → `start.bat`) or on the next build/restart.
  **Phase 2 needs the regenerated client.**
- Files: `prisma/schema.prisma`, the new migration, `.vpanel/verify-phase1.ts`.
