## Cloudflare question — answered, with the trade-offs

**Asked:** "What script should I connect to Cloudflare so the request volume for
xhttp is reduced and it is easily managed, so the user stays connected?"

**State at the time:** 5 configurations served (VMess xhttp 443/8443, VMess tcp
2083, VLESS tcp 2087, Trojan tcp/tls 2053); xray healthy; **RAM still critical —
236 MB free of 4095 MB** (WorkBuddyAI 1363 MB, Edge 241 MB, node 192 MB, xray
12 MB). The memory problem from 2026-09-28 was still active.

**The three facts the operator needed:**

1. **Cloudflare requires a domain.** You cannot point Cloudflare at a bare IP.
   The operator has NO domain (standing constraint, rule 16), so the normal route
   is closed. The only domain-free option is a **Cloudflare quick tunnel**
   (`cloudflared tunnel --url http://127.0.0.1:PORT`), which yields a
   `*.trycloudflare.com` hostname — a **temporary** address that changes on every
   restart, which is the opposite of "users stay connected".
2. **Cloudflare does not reduce proxy traffic.** A proxy carries no cacheable
   content, so every request still reaches the origin. What Cloudflare *can* do is
   hide the origin IP — which stops internet scanners and bots from hitting the
   ports directly — and absorb DDoS. It also adds a hop, so latency usually worsens.
3. **The measured problem was RAM, and Cloudflare cannot fix it.** Point 21.

**Useful compatibility finding:** the operator's ports — 443, 2053, 2083, 2087,
8443 — are **exactly the HTTP ports Cloudflare will proxy** (80, 443, 2053, 2083,
2087, 2096, 8443). So if a domain is ever added, no port changes are needed.

**Delivered:** `cloudflare-tunnel.bat` (inert until run) for the domain-free quick
tunnel, with all four caveats written into its header.

## XHTTP options — probed from the binary, then added to the panel

**Asked:** focus on xhttp; if the Xray core has options for it, add them to the
panel and prove the generation and the operation are correct.

**1. What this build accepts** (`.vpanel/xhttp-options-probe.ts`, one
`xray run -test` per candidate):

| accepted | rejected / dangerous |
|---|---|
| `path`, `host`, `mode` (auto \| packet-up \| stream-up \| stream-one), `extra.{scMaxBufferedPosts, scMaxEachPostBytes, scMinPostsIntervalMs, noSSEHeader, xPaddingBytes, xmux}`, `noGRPCHeader`, top-level `scMaxEachPostBytes` / `scMinPostsIntervalMs` | `mode: bogus` → "unsupported mode"; `headers` containing **"host"** → rejected (use `host`) |

**2. The trap that decided what to expose** (`.vpanel/xhttp-match-test.ts`,
throwaway server + real client):

| server | client | result |
|---|---|---|
| auto | auto | data flows |
| packet-up | auto | data flows |
| **stream-up** | auto | **NO DATA** |
| **stream-one** | auto | **NO DATA** |
| xPadding | none | data flows |
| xmux | none | data flows |

**A share link cannot carry `mode`**, so `stream-up` / `stream-one` would break
every client — they are NOT offered. This is the same class of outage as the
transports Xray 26 removed (rule 20): a setting the client cannot see.

**3. Added to the panel** (safe, server-side subset):
- `xhttpMode`: `auto` (default) | `packet-up` — `XHTTP_MODES` in `types.ts`
- `xhttpXmux` + `xhttpXmuxMaxCon` + `xhttpXmuxMaxWorkTimeMs` → `extra.xmux`
- `xhttpPadding` → `extra.xPaddingBytes`

xmux lets several requests share one connection — **the only option here that
actually reduces the request count on the node**, which was the operator's goal.
Wizard fields with Persian labels live in `config-generator/index.ts`, visible
only for `network=xhttp`.

**4. Proven:** `tests/xhttp-options.test.ts` (4 tests) covers the rendering, the
defaults and that `stream-up` is rejected. Live: applied to the VMess xhttp
configuration on 8443 → `config.json` shows
`{"path":"/","mode":"packet-up","extra":{"xmux":{"maxCon":8,"maxWorkTimeMs":15000}}}`
(the pre-apply `xray run -test` gate accepted it) and **a real client through the
delivered link still returned `HTTP/1.1 200 OK`** — the link carries none of those
options, which is exactly the point. 443 (still `auto`) also 200 OK.
