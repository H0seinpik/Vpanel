## Verified: traffic attribution is per-user even on a shared port (operator's main worry)

The operator asked: on a shared 443 (one config, many paths), is traffic still
attributed to the right user? **Answer: yes — proved live.**

The chain, each link verified in code AND in the running system:

1. `renderInboundFor()` (xray-service.ts:618-629) — for multi-user protocols it
   writes `clients: config.assignments.map(a => buildClient(..., clientEmailFor(a.id)))`.
   So **every assignment becomes its own client entry with a unique email**, even
   inside a shared-port member inbound.
2. Live `config.json`: each loopback member inbound carries exactly one client,
   email `vp-<assignmentId>`. Public 443 listener has no clients (it routes by
   fallback path).
3. Xray policy sets `levels.0.statsUserUplink/Downlink = true`, so Xray emits
   `user>>>vp-<id>>>traffic>>>{up,down}link` **per email**.
4. Proved live: after one `doctor --connect` pass, the stats API returned **two
   separate** `user>>>` counters (value 54 each) — one per assignment — while
   only `inbound>>>vpanel-*` counters existed before the connection.
5. `queryUserStats()` parses `^user>>>(.+?)>>>traffic>>>(uplink|downlink)$`
   (xray-service.ts:1230) → keyed by email.
6. `xray-worker.ts:91` → `assignmentIdFromEmail()` → `ConfigAssignment` lookup →
   `{userId, configId}` → `recordTrafficSamples()` increments user + assignment +
   configuration + subscription counters.

**Key point:** `user>>>` counters **only appear after a client connects** — an
empty stats query is NOT a bug, it just means no traffic yet. Do not misread
`statsquery -pattern user>>>` returning `{}` as broken accounting.

## ROOT CAUSE FOUND: "tcp pings but does not connect" = transport mismatch

Operator: *"tcp که میدم پینگ میده اما کانکت نمیشه"* — "when I set tcp it pings but
does not connect."

**This is the whole mystery, solved.** The operator was **manually setting the
transport to `tcp` inside their client app**. None of the four configs are `tcp`
— all four are `ws`. Forcing `tcp` in the client breaks a working link.

**Reproduced deliberately** (`.vpanel/transport-probe.ts`, same server, same port,
same credential, only the transport differs):

| transport | ping | data |
|---|---|---|
| `ws` (what the link says) | PING OK | **HTTP 204** — works |
| `tcp` (forced by the operator) | PING OK | **HTTP 000** — nothing |

**Why the ping misleads:** the ping tests the *port*, not the configuration. Port
443 is open because Xray listens on it, so the ping succeeds **even when the
transport is wrong**. It is not evidence the config works.

**Why tcp fails on a shared port:** routing is by request **path**. The public 443
listener is `vless+tcp+tls` carrying fallbacks (`/vp-6pnhhdgg` → :20600,
`/vp-tgqq2p1g` → :21854, `/vp-5sa3fcfl` → :22568, `(default)` → :1). Each fallback
target is a **separate `ws` inbound**. A `tcp` client completes the TLS handshake
on 443, sends **no HTTP request with a path**, matches no fallback, and is handed
to `(default) → dest 1` (further processing / blackhole). Result: port open, ping
fine, zero data. `tcp` carries no path and therefore **cannot** be routed from a
shared listener.

**Fixes shipped this session:**
- Wizard `FieldControl` gained a `network` branch — when the chosen port is
  already in use, a `tcp` selection shows an inline red explanation
  ("this port stays open and answers pings, but no data ever passes — use ws").
  `sharedPortTransportWarning` is passed from both the basic and advanced field
  lists.
- 4 new tests in `tests/sharing-defaults.test.ts` pin the trap: `tcp` + shared port
  is refused, the reason names `tcp` **and** `path`, the fix names `ws`, a supplied
  path does not rescue it, and the same config on a **free** port is untouched
  (tcp is legal alone).

**Tests 234 → 238 (14 files), tsc clean.**

## BUG FOUND AND FIXED: xhttp and grpc cannot be shared at all

The operator chose "migrate everything to xhttp" (they use **v2rayNG**). Before
touching the live port I proved the migration first — and it would have made
things **worse**.

**Measured, one fallback parent, one member per transport, real client + real
fetch for each** (`.vpanel/which-transports-can-share.ts`):

| transport | result | verdict |
|---|---|---|
| `ws` | HTTP 204 | **WORKS** |
| `httpupgrade` | HTTP 204 | **WORKS** |
| `xhttp` | HTTP 000 | **FAILS** — `failed to dial to localhost:1` |
| `grpc` | HTTP 000 | **FAILS** — `failed to dial to localhost:1` |

`xhttp` and `grpc` **accept a `path` in their stream settings** — which is exactly
why they were on the shareable list — but the request never matches a fallback, so
the node hands it to the **default destination (`dest: 1`)** and no traffic flows.
A path *field* is not the same as a path the **fallback parent can match on**.

**The bug:** `sharing-defaults.ts` `SHAREABLE_NETWORKS` and `port-sharing.ts`
`shareIneligible()` both listed `xhttp` and `grpc` as shareable. So the wizard
would choose them for a busy port, the renderer would emit a shared listener with
those members, and the result **looks completely healthy and carries nothing** —
the operator's "port is open but no data" report, produced by the panel itself.

**Fixed:**
- `SHAREABLE_NETWORKS` reduced to `['ws', 'httpupgrade']`, with the measurement
  recorded in a comment so nobody re-adds them on theory alone.
- `shareIneligible()` now refuses `xhttp`/`grpc` **with a distinct, accurate
  message**: it does NOT say "no path" (they have one) — it says the transport
  "cannot be reached through a shared port" and the fix offers **both** `ws` and
  "give this configuration its own port" (both are valid).
- Tests: `isShareableNetwork` now rejects `xhttp`/`grpc`; 6 new tests pin the
  refusal, assert the reason names the transport and mentions "shared", assert the
  fix offers both options, and assert the reason does **not** claim "no path".

**Tests 238 → 244 (14 files), tsc clean.**

not shareable. The panel was already using `ws`, which is the correct and working

## PERMANENT FIX: the two-worker outage can no longer happen

Operator: *"هر کاری که میتوانی انجام بده و این مشکل را برای همیشه رد کن"* — "do
whatever you can and close this problem for good."

Three independent layers were added. Each one alone would have prevented the
12-minute wipe; together they make it structurally impossible.

### Layer 1 — the empty-render guard (`src/services/render-guard.ts`)

`syncXray()` treated `rendered.config === null` as "the operator removed
everything" and wiped `config.json` immediately. Correct for a real deletion,
catastrophic for a transient read.

`decideEmptyRender()` now requires the empty render to be confirmed on
`EMPTY_RENDER_CONFIRMATIONS = 2` consecutive ticks. The first empty read
returns `action: 'hold'` — the previous config stays applied and the node keeps
serving. The counter is persisted in `.vpanel-state.json` (`emptyRenderCount`)
so it survives a restart and is shared across ticks.

`assertRenderIsApplicable()` is a second gate: a render with inbounds but no real
port, or no outbound, is refused rather than applied — because Xray refuses to
start on a malformed config and takes every port down with it.

**Proof** (`.vpanel/render-guard-proof.ts`, replaying the exact outage sequence):
```
empty render #1  ->  HOLD (node keeps serving)
empty render #2  ->  APPLY (node cleared)
```
Renders 3–6 behave as 2. The wipe can no longer *start* on a single bad read.

### Layer 2 — the single-writer lock (`src/services/worker-lock.ts`)

`workers/lib/lock.ts` falls back to an **in-process** `Set` when Redis is absent
— and Redis is absent here (`REDIS_URL` is set but nothing listens). So two
worker *processes* had **zero** mutual exclusion. That is the whole mechanism of
the outage, and the log says it plainly:

```
{"scope":"lock","message":"Redis unavailable — using in-process lock only"}
```

`acquireWorkerLock()` writes the owner pid to `.vpanel-worker.lock` in the node
dir and refuses to start a second daemon (exit code 2). A lock whose owner is
provably dead is reclaimed automatically, so a crash never leaves the node
permanently unmanaged.

**Proof, live:**
```
$ npm run worker  (with one already running)
{"level":"error","scope":"scheduler","message":"refusing to start: another worker owns the node config",
 "meta":{"reason":"another worker daemon is already running (pid 1972 …)",
 "fix":"Stop the other worker first — only one may run."}}
exit code 2
```

### Layer 3 — `start.bat` no longer creates a second worker (`windows/start.ps1`)

This is how the duplicate was actually born. The "already running?" check tested
**only `webPid`** — so a dead web server with a live worker made `start.ps1`
launch a *second* worker beside the surviving one. Now the script resolves a live
worker (recorded pid, then command-line fallback), reuses it, and never starts a
second. `stop.ps1` also removes the lock file so a restart is always clean.

### Auto-heal verified

`syncXray()` already restarts Xray when the hash matches but the process is gone,
so the 15 s tick is the watchdog. Tested by killing Xray outright:
`taskkill /F /IM xray.exe` (pid 9044) → **new pid 9444 listening on 443 within
25 s**, log line `node config applied: inbounds=3, ports=[443], "Xray started"`.

### Observability

## "It does not connect and doctor fails" — a WEDGED WORKER, not a path problem

Operator: *"به کانفیگ کانکت نمیشه و توی doctor fail دارم با این که ایکس ری رو ران

### Also found: `GET /api/health` was being CACHED

### The fix — three more guards

1. **Heartbeat** (`src/services/worker-lock.ts`): `writeWorkerHeartbeat()` writes
   `.vpanel-worker.heartbeat` (pid + per-job `{at, runs, failures}`) after every
   job run via `persistHeartbeat()`; `readWorkerHeartbeat()` returns
   `wedged: true` only when the pid is **alive** but the heartbeat is stale. A
   dead pid is "gone", not wedged. `GET /api/health` exposes
   `workers.heartbeat`, and a wedged worker makes the whole endpoint `degraded`.
2. **Watchdog + fatal handlers** (`workers/index.ts`): `startWatchdog()` exits 3
   and releases the lock when a critical job goes stale; `unhandledRejection` /
   `uncaughtException` exit 4 the same way. Both deliberately **leave** the
   heartbeat file — it is the evidence of why the worker died.
3. **`watchdogAllowanceMs(intervalMs) = intervalMs * 3 + 30 s`** (pure, exported,
   unit-tested) — see below.

### My own bug, caught by the watchdog firing — the most useful signal of the session

The first watchdog used a **flat 90 s**, and it killed a healthy worker within
minutes:

eager than its own schedule is a self-inflicted outage. Replaced with the

## Session 2 — "SHADOWSOCKS does not count traffic" + "the Sign in button never enables"

Two separate reports, both reproduced and both fixed and proven live.

### 1. Shadowsocks traffic was never attributed (root cause: STALE WORKER)

The operator's report: *"Server 01 · SHADOWSOCKS ترافیک رو نمیشماره"*.

**Measured on the live node first**, and it was unambiguous:
`inbound>>>vpanel-yvmy5w>>>traffic>>>uplink = 708139` / `downlink = 2618675` —
the busiest configuration on the node — with **zero `user>>>` counters for it**.

Two independent causes, and BOTH had to be fixed:

**(a) `MULTI_USER` omitted `SHADOWSOCKS`.** `buildClient()` therefore never
received an `email`, and Xray's per-user statistics are keyed on the client
`email` (`user>>>EMAIL>>>traffic>>>uplink`). No email ⇒ the traffic is carried
but unattributable. Fixed by adding SHADOWSOCKS to `MULTI_USER`.

**(b) But multi-user Shadowsocks is NOT a superset of the single-user shape.**
Measured with `xray run -test` on the real binary — four shapes:

| shape | verdict |
|---|---|
| `{ method, password }` | ACCEPTED (single-user, no email) |
| `{ clients: [{ method, password, email }] }` | ACCEPTED (multi-user) |
| `{ method, clients: [{ password, email }] }` | **REJECTED `unsupported cipher method:`** |
| `{ method }` (no password) | REJECTED |

So the cipher must be **per client**, and the inbound-level `method`/`password`
must be **removed** — leaving them makes Xray refuse to start the whole node.

Encoded in the exported pure `applyClients()` in `xray-service.ts`: for
SHADOWSOCKS it deletes `INBOUND_LEVEL_CREDENTIAL_FIELDS` (`method`, `password`)
from the settings and injects the default `method` into every client. Result:
`{ network, clients: [{ method, password, email }] }`.

**(c) The reason the source fix did not appear on the node: the worker was
running PRE-EDIT code.** Worker pid 1132 started 01:08 local; `xray-service.ts`
was saved at 02:22. `tsx` had the old module in memory, so its 15 s reconcile
kept faithfully re-rendering the OLD single-user shape. This is rule 4 in
action — *after editing worker code, restart the worker*. Restarting it produced
`"node config applied" … "config changed - Xray restarted"` on the first tick.

**Proven end to end, live** (`.vpanel/ss-live-proof.ts`): start a real Xray
client → dial 127.0.0.1:8443 with the real credential → push a SOCKS5 request →
query the stats API.

```

after     uplink = 192   INCREASED
again     uplink = 384   INCREASED
user>>>vp-cmul12n84000r83v3kign4yk2>>>traffic>>>uplink = 384
```

And the last link (`.vpanel/ss-db-proof.ts`):
```

                window=…T09:31 up=192 src=AGENT
traffic_usage sum = 384
configuration.trafficUsedBytes = 384     ← matches the node exactly
```

The operator's existing `ss://` link needed **no change**: it decodes to

### 2. "The Sign in button does not light up" (the form was hydration-gated)

The operator: *"195.248.241.251:3000 از سیستم دیگه … دکمه ساین این روشن نمیکنه"*.

Reproduced by curling the server-rendered page:

```
<button class="…" disabled="" type="submit">Sign in</button>
```

The cause was `disabled={!identifier || !password}`. Both fields start `''`, so
the **server** HTML shipped the button already disabled, and it could only ever
become enabled once React hydrated on the client. On a browser that never runs
the JS chunk (slow LAN load, a proxy stripping it, a stale asset, an old
browser) the operator types a *correct* password and the button stays dead
forever. The page looks perfect and is unusable.

**The rule, generalised: a form control's initial enabled state must never be
derived from client state that begins empty.** It makes the control's
availability a function of hydration, which the operator cannot see or fix.

Fix: `disabled` derives ONLY from `loading` (false on the server), validation
moves into `onSubmit`, the native `required` attributes stay as the no-React
safety net, and a `<noscript>` block now explains a JavaScript-disabled browser
instead of leaving a form that silently does nothing.

```

<input … required="" name="identifier" value=""/>
<input … required="" name="password" value=""/>
<noscript> present
```

New test `tests/login-form.test.ts` (6 tests) asserts on the source, because the
test environment is `node` (no jsdom) and — more importantly — the bug was in
the *server* HTML, which mounting the component would not even exercise. It
fails loudly if `disabled` is re-derived from the fields.

### 3. Structural bug found while investigating: the PANEL was a second writer

`proc-map.ts` showed `xray (pid 9956) parent 7000 is NOT a worker` — 7000 was
`next start`, i.e. **the panel had spawned the node process.**

The reason: `syncXray()` had **no lock check at all**, and the panel is a
genuine writer — every configuration mutation calls `triggerXraySync()`
(`config-service.ts`, 5 call sites). So the panel and the worker were both
reconciling `config.json`, with no mutual exclusion. Combined with the stale
build, that is a direct path to "I fixed it but the node reverted": the panel
renders from its own in-memory code, which can predate the fix the worker has.

Closed by adding `mayWriteNodeConfig(xrayDir)` to `worker-lock.ts` and calling it
at the top of `syncXray()`:
- **we own the lock** → write (this is the worker; also the normal path)
- **the recorded owner is dead** → write (never abandon the node)
- **a live foreign process owns it** → **defer**, and say which pid/role owns it
- `force: true` (the explicit `xray:sync` CLI) bypasses the *refusal*, but a live
  foreign owner is still reported rather than silently overwritten.

5 new tests, all passing.

### What `core instance is nil` actually means

The string does not exist anywhere in VPanel —
`grep -ri "core instance is nil" src/ workers/ .next/` is empty. It is the phone
app reporting that **its own bundled proxy engine never started** ("core" =
the app's Xray/V2Ray process; "nil" = no handle to it). The app then reports the
generic "cannot detect internet". A configuration cannot cause this: the app fails
before it ever dials the server, which is why the same app can fail on ONE profile
while the other three work — the other three were already started/imported
successfully, and this profile's start attempt crashed the core.

Because a shared 443 listener advertises `alpn: ["http/1.1"]`, and several mobile
clients mis-handle an ALPN/ALPN-less or SNI-less profile, the trigger is usually
one of: the profile was hand-edited rather than re-imported; "Enable Mux" is on
(it breaks ws); the app is an older build; or the app's core was killed by the
system and never restarted.

### Operator fix (in order)

1. **Delete the 10Gb profile and re-import the link** — never hand-edit. Most
   common cause by far.
2. **Turn off "Enable Mux" / multiplex** for this profile.
3. **Force-stop the app**, clear its cache, reopen (the core restarts).
4. Update the client app to the current build; reboot the phone if needed.
5. If it still fails, screenshot the app's own log — that names the core error,
   which the generic message hides.

### Tooling

`.vpanel/config-diff.ts` (per-config ceilings/quota/fallback order),
`.vpanel/path-route-proof.ts` (walks the fallback table and routes a real request
through a *chosen* path via `PROBE_PATH`; also A/B-proved that the working config

that collapsed `Path`/`PATH` then failed on `http_proxy` / `HTTP_PROXY`. This is a

- A `run_in_background: true` task survives for hours (the previous worker lived

- `Start-Process`-spawned children survived a foreground tool call (observed 13
  min, until deliberately killed).
- Consequence: **I cannot fully verify the user's logon path from here.** At a real
  logon (started by explorer, no sandbox) both mechanisms behave normally.

**Watchdog false positive, found and fixed.** `watchdog.log` recorded
`unhealthy check #1 (panel=true worker=false)` on a healthy stack.
`writeWorkerHeartbeat()` used a plain `writeFileSync`, so a reader could see a
**partially written** file, `JSON.parse` would throw, and the reader would conclude

1. `src/services/worker-lock.ts` — the heartbeat is now written to a temp file and

2. `scripts/watchdog.mjs` — `workerFresh()` retries once after 750 ms, so a read
